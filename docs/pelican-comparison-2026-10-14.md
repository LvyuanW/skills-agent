# 鹈鹕骑自行车三次测试分析报告

比较对象：skills-agent 的 demo4、demo5，以及 Claude Code + DeepSeek Flash 的本机测试。时间统一为北京时间；报告日期为 2026 年 10 月 14 日。

**demo5 的执行方式确实进步了，但视觉品质与验收质量没有同步提高。** 它在约 82 秒内写出首版 HTML，随后真正进行了看图、修改和独立审查；因此，质量下降不能解释为没有读 skill、没有看图或跳过 review。更直接的问题是：它对造型和构图较早表示满意，检查集中于局部机械关系，并把有限验证扩展成了整体正确的判断。本次复核还发现最终产物的山丘在 9 秒和 12 秒循环边界发生可见跳变。

Claude 的优势主要出现在初版之后：根据图片反复重塑喙、喉囊、翅膀和姿态，连续三轮修改仍未满足时继续修。但它同样有首轮长思考、工具阻塞，以及最终验证结论超过证据的问题。demo4 也有真实反馈循环，初次交付的美术风格已经形成；后续用户纠错主要补齐传动系统。

## 对比范围和统计口径

三次初始要求实质相同：在指定目录制作原生 HTML 的鹈鹕骑自行车 SVG 动画，自主决定工作方式，验证动画表现，一切就绪后交付。

- demo4：10 月 11 日，包含首次制作、用户指出前齿轮不转，以及两次断线后的“继续”。视觉对比采用用户从垃圾桶恢复并明确确认的最终 HTML。
- demo5：10 月 14 日，一轮用户请求，包含一次真实的独立 review 子 Agent。
- Claude：10 月 14 日，一轮用户请求，最终回答在 21:59:04；之后的系统记录不算继续工作。

skills-agent 只统计完成的 `message`，不重复累计流式片段及其 raw 副本。Claude 按 `message.id` 去重，工具按调用 ID 去重。图片数是返回模型的原生图片块数，含局部图、接触表和重复检查，不等于美术改进轮数。子 Agent 的内部对话不展开，只展示目标、发现和主 Agent 的处理。

## 提速与品质下降如何同时发生

### 提速发生在实现和反馈获得的时机

demo4 把较完整的实现集中在首个大响应中，首版耗时 9 分 25 秒；demo5 将生成器、模板和组装分开，约 82 秒已有首版，约 85 秒已经看见结果。feedback skill 的既有截图能力也被直接使用，减少了从头搭建截图流程的步骤。

这是行为上的改善。但单次响应更短、首版更早，不自动产生更好的构图和造型。demo5 含 review 的累计输出甚至高于 demo4 首次交付含辅助调用的输出；其运行更快不能简单等同于“少做了工作”。模型服务吞吐、响应等待和运行环境也影响时间，三次日志不能把这些因素完全分离。

### 视觉判断停在了较低的完成标准

demo5 的主要修改是缩翼、减细腿、降低身体、露出车架和修机械连接。它多次表示画面已正确，review 也认可了题材可辨认。最终图中的小主体、细白折线腿、长条翼和线状喉囊没有被进一步重塑。

Claude 则把“像鹅”“像香蕉”“像木板”“喉囊与上颚脱节”当作仍需处理的问题，改动了具体形状，再用新图决定是否继续。两者都看图，差异在于**如何解释图片，以及什么程度才算完成**。不能仅靠提高看图次数、增加一遍 reviewer 或恢复长时间思考来保证品质。

demo4 的大主体、粗轮廓和完整喉囊在初交付时已经存在，说明初始设计也贡献了差异。本次无法证明更长的首轮推理造成更好设计；它可能同时包含有效设计和重复推演。

### 自己生成的数值正确不等于浏览器表现正确

demo5 初始断言证明生成器算出的脚坐标位于圆上，但未证明浏览器中的曲柄围绕同一中轴旋转。主 Agent 在日志 41750、46450 已宣称确认脚踏正确，review 却在真实 HTML 中发现两处 SMIL `rotate` 缺少中心，并用对照图片证实曲柄脱离。主 Agent 随后承认此前误读了图中的异常条。

review 在这里有效，因为它对实际产物提出可反驳的检查，并找到了独立证据。有效审查的价值来自这种方法，不来自最终有一张 PASS/FAIL 表。

## 对 skills-agent 的改进含义

建议保留 demo5 已表现出的尽早落地、持续反馈和独立 review。后续若调整，重点可以落在现有技能内容和选择标准上，无需新增基础设施：

1. **把视觉品质纳入交付判断。** 对视觉任务，审查除“题材可辨认、没有明显故障”外，还应检查主体比例、轮廓、遮挡、构图和风格是否支持用户目标。提出具体可观察的问题；避免泛泛要求“更精美”，也不要为简单任务强制一套设计流程。
2. **先核对实际实现的覆盖范围，再选择检查。** 动画除了脚踏，还有山丘、云和道路；分别考虑其周期边界。其他任务同理：不能把一个局部函数、格式或自定义指标的通过外推到整个目标。
3. **review 同时检查产物和完成声明。** 把“确实观察到”“只作了局部检查”“尚未验证”区分清楚。功能底线通过之后，仍应指出影响用户体验的具体问题；不要求为了审查而审查。
4. **不要自行添加实现禁令。** “原生 HTML”并不等于“禁止 JavaScript”。实现选择应服务于目标，不应通过额外限制缩小模型的可选方案。

这次证据支持改进完成标准和检查方法，不支持回退到长时间内部预演，也不支持把 shell + skills 换成大量固定工具才能提高质量。若要评估某次提示词修改是否稳定改善品质，需要在相同设置下重复相同任务，并分别记录速度、实际缺陷和视觉评价，不能只看一次输出或工具数量。
